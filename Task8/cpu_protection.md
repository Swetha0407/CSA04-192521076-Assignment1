# Task 8 – Evaluate CPU States and Protection

## 1. Aim

To evaluate how computer hardware protects the hospital system using CPU execution modes, privileged instructions, interrupts, timer interrupts, and memory protection. The task also compares polling and interrupt-driven approaches for monitoring bedside sensors.

## 2. User Mode and Kernel Mode

An operating system uses two execution modes to provide protection and control over system resources.

### User Mode

- Applications execute with restricted privileges.
- They cannot directly access protected hardware or execute privileged instructions.
- They request operating-system services through system calls.
- Applications such as bedside monitoring software and nurse applications generally execute in user mode.

### Kernel Mode

- The operating-system kernel executes with full privileges.
- It can access hardware, manage memory, handle interrupts, and control processes.
- It can execute privileged instructions.
- Critical operating-system operations are performed in this mode.

### Mode Bit

The CPU maintains a mode indicator, commonly called the mode bit, to identify the current execution mode. Hardware uses this information to restrict access to privileged operations.

When an application requests a protected operating-system service, execution switches from user mode to kernel mode. After the service is completed, control returns to user mode.

**Application to the hospital:** Bedside monitoring applications should not have unrestricted access to hardware or operating-system controls. Kernel mode provides controlled access to these resources.

## 3. Privileged Instructions

Privileged instructions are special CPU instructions that can only be executed in kernel mode.

Examples include:

- Disabling and enabling interrupts.
- Modifying memory-management settings.
- Controlling hardware devices.
- Performing certain processor control operations.

If a user-mode application attempts to execute a privileged instruction, the processor prevents the operation and raises an exception or trap.

**Hospital application:** A faulty bedside monitoring program must not be allowed to disable interrupts or modify hardware configuration. Restricting privileged instructions prevents ordinary applications from interfering with critical operating-system operations.

## 4. Interrupts, Traps and Timer Interrupts

### Interrupts

An interrupt is an asynchronous signal that requests the CPU's attention. It allows hardware devices to notify the processor when an event requires processing.

For example, a bedside monitoring device can generate an interrupt when a new sensor reading becomes available.

### Traps

A trap is a synchronous event generated by the currently executing instruction or an intentional request for an operating-system service.

Examples include:
- Requesting a system call.
- Attempting an invalid operation.
- Accessing memory without permission.

The operating system handles the event and takes the appropriate action.

### Timer Interrupts

A timer interrupt is generated by a hardware timer at regular intervals. It allows the operating system to regain CPU control and perform scheduling operations.

For example, if a program enters an infinite loop, a timer interrupt allows the operating system to pre-empt it and schedule another process.

Timer interrupts help prevent one ordinary application from continuously occupying the processor.

## 5. What Happens If Any Program Can Disable Interrupts?

In the hospital environment, allowing every application to disable interrupts would create a serious safety risk.

Consider a situation where a bedside monitoring application disables interrupts because of a programming error.

The following problems could occur:

1. Other monitoring devices may not receive timely CPU attention.
2. New sensor readings and alarm events may remain pending.
3. Timer interrupts may not be serviced normally.
4. The operating system may lose its normal scheduling opportunities.
5. An abnormal patient reading could go unnoticed beyond the required 10 ms.

This could delay critical medical alarms and affect patient safety.

Therefore, disabling interrupts must be restricted to privileged kernel operations. The operating system must also keep interrupt-disabled sections short to avoid delaying other critical events.

## 6. Hardware Memory Protection

Modern processors use a Memory Management Unit (MMU) to provide memory protection.

The MMU works with memory mappings and access permissions maintained by the operating system.

Memory protection works as follows:

1. Each process receives its own virtual address space.
2. Page tables map virtual addresses to physical memory.
3. Access permissions specify whether a process can read, write, or execute a memory page.
4. If a process attempts to access memory without permission, the processor raises a protection fault.
5. The operating system handles the fault and prevents unauthorized access.

**Hospital application:** A nurse's tablet application should not directly access the memory belonging to the patient-record database process. Memory protection prevents one process from reading or modifying another process's protected memory.

This isolation reduces the impact of faulty or malicious applications and protects sensitive hospital data.

## 7. Alternative Concept – Polling Instead of Interrupts

Polling and interrupts are two approaches used to detect events from hardware devices.

### Polling

Polling is a method in which the CPU repeatedly checks whether a device has produced new data or requires attention.

For example, a bedside monitoring system may continuously check whether a sensor has reported an abnormal reading.

### Interrupt-Driven Approach

In an interrupt-driven approach, the hardware device signals the CPU when an event occurs. The operating system then handles the event.

For example, a sensor can generate an interrupt when a new reading becomes available, instead of requiring the CPU to repeatedly check it.

## 8. Worst-Case Detection Delay

Let:

- \(T_p\) = Polling interval.
- \(L_i\) = Interrupt response latency.

### Polling Delay

If an abnormal reading arrives immediately after the CPU checks the sensor, the system may have to wait almost one complete polling interval before detecting it.

Therefore:

$$
D_{\text{poll,max}} \approx T_p
$$

For example, if the polling interval is 20 ms, the worst-case detection delay is approximately 20 ms. This cannot satisfy the hospital alarm requirement.

If the polling interval is reduced to 5 ms, the maximum nominal polling wait becomes approximately 5 ms. However, additional time is required to process the reading and activate the alarm.

### Interrupt Response Delay

In an interrupt-driven system, the device signals the CPU when an event occurs.

The detection delay depends on interrupt response latency:

$$
D_{\text{interrupt}} \approx L_i
$$

The interrupt response latency must be bounded and measured under the expected system workload.

For the hospital's 10 ms requirement, the complete alarm response time, including detection, processing, communication, and alarm activation, must remain within 10 ms.

## 9. CPU Time and Power Consumption

| Factor | Polling | Interrupt-driven |
|---|---|---|
| CPU usage | CPU repeatedly checks sensors. | CPU handles events when signalled. |
| CPU time | Can waste CPU cycles during continuous checking. | Uses CPU time mainly when events require processing. |
| Power consumption | Can consume more power due to repeated checks. | Usually more power-efficient when events are infrequent. |
| Response time | Depends on the polling interval. | Depends on interrupt response latency. |
| Suitability | Useful when a carefully selected polling interval is acceptable. | Suitable for event-driven monitoring. |

For 500 bedside monitors, continuously checking every sensor can consume significant CPU resources and power. Interrupt-driven monitoring can reduce unnecessary checking and provide faster event notification.

However, interrupts alone do not guarantee the 10 ms deadline. The operating system and hardware must be designed and tested to provide a bounded worst-case response time.

## 10. Evaluation and Recommendation

For the smart hospital, hardware protection is essential because multiple applications and devices operate simultaneously.

The following measures should be used:

- Run ordinary applications in user mode.
- Restrict privileged instructions to kernel mode.
- Use timer interrupts to support CPU scheduling.
- Use hardware interrupts for event-driven sensor notification.
- Apply MMU-based memory protection to isolate processes.
- Prevent ordinary applications from disabling interrupts.
- Measure and verify the worst-case alarm response time.

An interrupt-driven approach is generally more suitable for bedside monitoring than continuous polling because it avoids unnecessary CPU activity and provides event-based notification.

The final design must ensure that all monitoring alarms are detected and processed within the required 10 ms deadline.

## 11. Conclusion

This task evaluated how hardware protects the hospital system through user mode, kernel mode, privileged instructions, interrupts, timer interrupts, and memory protection.

It also demonstrated the risks of allowing ordinary programs to disable interrupts and explained how the MMU prevents unauthorized memory access between processes.

The comparison of polling and interrupts showed that polling can waste CPU time and power, while interrupt-driven monitoring is generally more efficient for event-based sensor communication. Proper hardware and operating-system protection are therefore essential for maintaining patient safety and meeting the hospital's real-time requirements.
